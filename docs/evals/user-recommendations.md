# Проверки рекомендаций по пользовательским примерам

План проверки от 2026-10-31. Источник — `testsoptions.docx`, три ситуации,
уточнения пользователя и `data/evals/user-recommendation-cases-v1.json`.

Критерии определены до прогона:

- Модель видит только исходный запрос, контекст слушателя и обычный каталог.
  Положительные/отрицательные ответы и их объяснения не передаются модели.
- Каждый случай запускается с отдельной временной историей и профилем.
  Указанные в контексте исполнители используются как тестовые ориентиры;
  никаких оценок прослушивания не создаётся.
- Изменение фильтров проходит отдельный шаг явного подтверждения в тестовом
  сценарии, затем бесплатный подбор. Это имитация нажатия пользователя.
- Проверяем существование карточек, отсутствие повторов, пять результатов,
  сохранение hip-hop, а в rage-сценариях — принадлежность релизов rage.
  Третий запрос должен выбирать surprise. Недостаточная выдача фиксируется как
  невыполненное ожидание, даже если приложение корректно объяснило её причину.
- Наличие артистов из положительного списка — диагностический показатель,
  а не требование выдать только эти имена. Список не исчерпывающий, и пользователь
  указал артистов, а не одобрил каждый их альбом.
- Отрицательные примеры относятся только к своему запросу. Их появление
  фиксируется как ошибка соответствия ожиданиям.
- Не более двух широко известных вариантов из пяти. Без явных меток известности
  проверка возвращает `needs_labels`, а не успех. Число оценок AOTY не заменяет
  глобальную известность, незнакомость пользователю — тоже.
- В учитываемых примерах должен быть подтверждённый AOTY/RYM-источник. Slug
  исключён по указанию пользователя. Статусы источников хранятся отдельно от
  наличия исполнителя в локальном каталоге.
- Музыкальное соответствие, мягкость/агрессивность и уместность неожиданности
  остаются человеческой оценкой. Общее `passed=true` без неё недопустимо.

Первый прогон измеряет исходное поведение. Правки каталога и ранжирования
проводятся после сохранения исходного отчёта, чтобы сравнение было проверяемым.
Один прогон на случай — диагностика, не оценка стабильности.
Проверяется сервис веб-чата; это не проверка запущенного HTTP-сервера или браузера.

## Как запускать

Из корня проекта, бесплатно — проверить наличие исполнителей в каталоге:

```bash
uv run python -m discovery.evals.user_run
```

Проверить три исходных запроса через настроенную модель:

```bash
uv run python -m discovery.evals.user_run --live
```

Второй вариант использует общий журнал расходов приложения и дополнительный
предел $0.01 на весь запуск, включая повторы. Все истории и профили временные;
аккаунты сайта не изменяются. После предложения новых фильтров сценарий
имитирует их подтверждение и бесплатную подборку. Ошибка провайдера или просьба
уточнить запрос не заменяется успешной бесплатной выдачей.

Отчёты JSON и Markdown сохраняются в `artifacts/evals/user-<время>.*`.
`--output <новый-путь>.json` задаёт имя отчёта; существующий отчёт не перезаписывается.
В отчёте есть запрос, предложенные фильтры, карточки, провалы проверок, стоимость,
хеши кода/каталога/примеров и отсутствующие музыкальные ориентиры. Совпадение
имени в каталоге — предварительная диагностика, не доказательство совпадения
одноимённых артистов между источниками.

Код завершения: `0` для проверки покрытия, `1` при выявленном провале live-сценария,
`2` если автоматические проверки прошли, но ещё нужна человеческая оценка.
Неполная выдача остаётся провалом требования «пять вариантов» даже при честном
предупреждении. `passed` не становится истинным автоматически: оценка звучания
и разметка известности ещё не собраны.

## Как пользователь влияет на результат

Достаточно написать обычным текстом: запрос, какие ответы подходят, какие нет,
и почему. Codex переносит это в набор примеров с сохранением исходных слов.
Новый прогон показывает, приблизились ли ответы бота к этим ожиданиям.

После прогона полезно оценить конкретные карточки: «этот подходит, потому что…»,
«этот слишком мягкий/похож на уже знакомое…». Это уточняет критерии следующего
сравнения. Само добавление примера не обучает модель и не меняет оценки аккаунта.
Изменения каталога, обработки запроса или ранжирования проверяются отдельно.

## Исходный результат, 2026-10-31

Сохранён до изменения каталога, промпта или ранжирования:
`artifacts/evals/user-cases-baseline-20261031.json` и соседний `.md`.
Модель `openai/gpt-5.6-luna`, три успешных HTTP-ответа провайдера, по одному
вызову на случай, всего **$0.0023597**. Это не три успешные рекомендации:

- «Похожее на Kendrick, меньше пения»: пять карточек — Mos Def, Tyler,
  Kendrick, Denzel Curry, Substantial/Burns. Структурные проверки пройдены;
  музыкальное соответствие и лимит известности не подтверждены. Бот вернул
  в том числе артиста-ориентир и исполнителя из контекста слушателя.
- «Rage с учётом вкуса»: Whole Lotta Red, Skeletrix Language, 2093 — только
  три релиза. Все имеют метку rage, но требование пяти вариантов не выполнено.
- «Исследовать границы рейджа»: просьба уточнить запрос, без карточек.
  Режим surprise не применён. Проверка входного контекста подтвердила, что
  `rage` присутствовал в словаре, отправленном модели; отсутствие этого ID
  не объясняет отказ. Причину выбора clarify один прогон не доказывает.

В каталоге всего три rage-релиза. Семь разных артистов из положительных
rage-примеров не находятся по имени. Подтверждённые страницы AOTY сохранены
в `artist_references`, но это ещё не импорт их релизов в рабочий каталог.
В первом примере отсутствует Demetrius, в контексте двух других — PARTYNEXTDOOR.

Технические проверки после добавления оценщика: **502 теста пройдены**, включая
15 новых и прежние восемь синтетических сценариев. Это проверяет корректность
кода, а не качество музыкальных рекомендаций.

Следующие изменения сравниваются с этим исходным отчётом: расширение покрытия
rage подтверждёнными релизами, обработка исследовательских запросов и оценка
конкретного звучания. Положительные примеры не следует превращать в скрытый
список обязательных ответов.
