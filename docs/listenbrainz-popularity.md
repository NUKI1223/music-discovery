# Известность релизов: слушатели ListenBrainz

Дата: 2026-11-10. Код: `src/discovery/catalog/listenbrainz.py`,
`src/discovery/ranking/baseline.py` (`_popularity`).

## Зачем

Раньше ранжировщик знал об известности 520 релизов из 45 643 (голоса MusicBrainz, 411 из
них — ноль). Режим «малоизвестное» поэтому почти ничего не находил. ListenBrainz отдаёт
число своих пользователей, слушавших группу релизов MusicBrainz, без ключа и под CC0.

## Как это устроено

Два файла лежат рядом с каталогом (`data/unified/community-genres-v4/`):

| Файл | Что в нём | Как часто обновлять |
| --- | --- | --- |
| `musicbrainz-ids.json` | ID группы релизов MusicBrainz для релизов каталога и причины, по которым ID не найден | один раз; продолжать после остановки |
| `listenbrainz.json` | число слушателей на дату сбора | чаще чем раз в 90 дней |

Сам `catalog.json` не меняется. Сайт и CLI (`recommend`, `agent-preview`) загружают
каталог через `load_with_listeners`: если рядом есть `listenbrainz.json` того же снимка,
каждому релизу из него добавляется наблюдение с источником `listenbrainz`. Битый, чужой
или отсутствующий файл не мешает запуску: каталог загружается без слушателей, в журнал
пишется предупреждение.

## Команды

Из корня проекта:

```bash
uv run python -m discovery.catalog.listenbrainz status
uv run python -m discovery.catalog.listenbrainz match
uv run python -m discovery.catalog.listenbrainz listeners
```

- `match` ищет ID в MusicBrainz: один запрос в 1,1 секунды, до восьми названий одного
  исполнителя в запросе. Полный прогон 2026-11-10 занял около 23 тысяч запросов и
  10 часов: ответ MusicBrainz часто идёт дольше паузы.
  Состояние сохраняется каждые 50 запросов и при остановке (`Ctrl+C`, SIGTERM, SIGHUP);
  повторный запуск продолжает с того же места. `--max-requests N` ограничивает один запуск.
  При сбоях связи команда делает паузы (5 с, 15 с, 1 мин, 5 мин) и останавливается только
  после пяти отказов подряд. Запросы, упавшие из-за сбоя связи, не записываются: после
  `complete` проверь `status` и, если `not_searched_yet` больше нуля, запусти `match` ещё раз.
  Одновременно работает только один `match`.
- `listeners` запрашивает слушателей для всех известных ID (по 500 за запрос, около ста
  запросов, меньше минуты) и целиком перезаписывает `listenbrainz.json`. Запускать можно в любой момент,
  в том числе до окончания `match`: в файл попадут уже найденные релизы.
- `status` показывает, сколько релизов сопоставлено, сколько осталось и возраст данных
  (`age_days`, `stale`).

После `listeners` перезапусти сайт: каталог читается при старте.

## Правило сопоставления

Релиз считается найденным, только если совпали нормализованные название и исполнитель
(весь кредит или один из указанных в нём исполнителей), а год первого издания отличается
не больше чем на один. Для имён вида «米津玄師 [Kenshi Yonezu]» подходит любая из частей.
Если подходящих групп несколько и они равноценны, релиз остаётся без ID (`ambiguous`).
Ничего не найдено — `absent`. Угаданных ID нет.

У 380 релизов ID найден, но ListenBrainz не вернул по ним данных. Нулевых значений в

До этого данные об известности были у 520 релизов.

## Как ранжировщик использует число

- Источник выбирается среди свежих наблюдений (не старше 90 дней) по алфавиту:
  `listenbrainz` раньше `musicbrainz`.
- Релизы сравниваются внутри группы «жанр + возраст» одного источника, не меньше
  30 релизов в группе. «Малоизвестный» — нижние 40 % группы.
- Сравнивается не собственное число, а эффективное: максимум из собственного и самого
  большого числа среди других релизов того же исполнителя в каталоге. Причина — ошибки
  привязки в ListenBrainz: у альбома известного исполнителя может стоять 1 слушатель.
  «Various Artists» и «[unknown artist]» в этом правиле не участвуют.
- Собственное число 0 никогда не делает релиз малоизвестным.
- В компонентах решения: `rating_count` — собственное число, `artist_peak_count` —
  эффективное. Версия ранжировщика `baseline-v7-artist-peak-popularity`.

## Ограничения

- Это пользователи одного небольшого сервиса, а не все слушатели. Аудитория ListenBrainz
  смещена к англоязычной и технической публике.
- Релиз без данных никогда не считается малоизвестным: фильтр видит только найденное.
- Правило по исполнителю делает оценку ближе к «редкости исполнителя»: малоизвестный
  альбом известного исполнителя не попадёт в «малоизвестное».
- Составной кредит («A, B») в каталоге — отдельный исполнитель, пик участников на него
  не переносится.
- Через 90 дней после сбора данные перестают учитываться. При загрузке устаревшего
  файла выводится предупреждение.
- У релиза с источником `listenbrainz` нет оценки, поэтому компонент `quality` для него
  не считается (в формуле используется нейтральное значение).
- Каждое обновление `listenbrainz.json` меняет хеш каталога. При следующей подборке в
  базу аккаунта записывается новая копия каталога, около 105 МБ на аккаунт.
- Слушателей видят только сайт и CLI. Streamlit, evals и автообучение загружают каталог
  без них.
- Версия признаков `genre-tags-v2-artist-frequency` не менялась, хотя `rating_count` и
  `rarity` для релизов с ListenBrainz теперь в другом масштабе. Обученной личной модели
  пока нет; перед обучением это нужно решить отдельно.
