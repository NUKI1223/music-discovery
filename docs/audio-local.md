# Локальные измерения аудио

`discovery.audio` анализирует предоставленный пользователем WAV. По умолчанию нужны только уже установленные NumPy и стандартная библиотека Python: сеть, OpenRouter, модели, транскрипция и поиск аудио не используются. Реальные аудиофайлы для проверки пока не предоставлены; тесты создают синусоиды и явно отмечают их `is_fixture=true`.

```bash
.venv/bin/python -m discovery.audio /absolute/path/track.wav \
  --track-id 'your-track-id' --release-id 'existing-catalog-release-id' \
  --output artifacts/audio/track.json
```

`track_id` и `release_id` указывает оператор. Название файла не используется для распознавания исполнителя, релиза, жанра или связи с каталогом; принадлежность указанного ID каталогу проверяет вызывающий код. Без `--output` в stdout выводится JSON. `--fixture` обязателен для сгенерированных и тестовых записей; обычный CLI ставит `is_fixture=false`.

Python API:

```python
from discovery.audio import analyze_wav

record = analyze_wav("track.wav", track_id="track-id", release_id="release-id")
features = record["features"]  # dict[str, float], только численные измерения
```

Поддерживаются integer PCM WAV 8/16/24/32 bit, 8–192 kHz, 1–8 каналов. Сжатый WAV и float WAV нужно заранее преобразовать локальным аудиоинструментом в integer PCM; конвертация не запускается автоматически. Ограничения: 1 секунда — 30 минут, до 512 MiB. Повреждённые заголовки, обрезанные данные и практически тихие записи отклоняются с кодом ошибки. Обработка идёт окнами, без загрузки полного аудио в память. SHA-256 вычисляется по всему WAV, включая заголовки; изменение метаданных файла во время анализа обнаруживается.

## Что измеряется

В `windows` находятся неперекрывающиеся окна длиной 0,5 секунды и остаток в конце записи. Их `start_seconds` / `end_seconds` относятся к исходному WAV. Каждый оконный `features` содержит доступные измерения:

| Поле | Определение |
|---|---|
| `rms` | Корень из среднего квадрата отсчётов всех каналов, в шкале PCM от −1 до 1 |
| `peak_amplitude` | Наибольший модуль отсчёта среди каналов |
| `crest_factor` | Пик / RMS; не вычисляется для тихих окон |
| `dc_offset_abs` | Средний по каналам модуль постоянной составляющей |
| `zero_crossing_rate` | Доля соседних отсчётов с разным знаком, усреднённая по каналам |
| `spectral_centroid_hz` | Центр масс амплитудного спектра после удаления среднего по каналу и окна Hann |
| `spectral_rolloff_85_hz` | Частота, ниже которой находится 85% суммы амплитуд спектра |

Спектры каналов усредняются по амплитуде, RMS считается по всем отсчётам. Сведение в моно не применяется: противофазные стереоканалы не превращаются в ложную тишину. `features` верхнего уровня содержит длительностно-взвешенные средние (`*_mean`) и стандартные отклонения (`*_std`) оконных измерений. Отсутствующие измерения не заменяются нулями: например, для тихого окна отсутствует спектральный центр. Одноотсчётный остаток отмечается `too_short`. Тишина определяется порогом RMS `1e-5` в нормализованной шкале PCM.

Высокий спектральный центр не является меткой «жёсткий звук», а RMS не является оценкой энергии исполнения или качества мастеринга. Эти признаки не определяют жанр, наличие вокала, манеру подачи или предпочтения пользователя. Такие поля перечисляются в `unknowns`. Функциональная структура без внешнего адаптера равна `null`.

## Контракт и происхождение

- `schema_version: audio-analysis-v1`, `feature_version: pcm-window-v1`.
- Явные `track_id`, `release_id`, `is_fixture`; SHA-256 исходного WAV.
- `sample_rate`, `channels`, `sample_width_bits`, `duration_seconds`.
- `features`, `windows`, `unknowns`, `structure`, `stems`.
- `provenance`: способ измерения, версия алгоритма и NumPy, абсолютный локальный путь, размер исходника, время создания.
- `config`: определения каналов, окон, спектра, усреднения и порога тишины.

Путь и ID — метаданные происхождения, а не численные признаки. Потребитель должен проверять версию признаков, целостность/связь записи, не использовать fixture-записи как реальные доказательства и не подмешивать эталонные оценки или ответы слушателя в `features`. Сам адаптер не читает аннотации, названия песен или жанры. Сырые признаки не подключаются к рекомендациям автоматически.

## Необязательная структура: allin1

Проверен официальный интерфейс [`allin1.analyze`](https://github.com/mir-aidj/all-in-one#usage-for-python) и его [реализация](https://github.com/mir-aidj/all-in-one/blob/main/src/allin1/analyze.py): он возвращает темп, биты, сильные доли и сегменты. Внутри также запускается разделение Demucs. Установка, первая загрузка весов и работоспособность настоящих моделей здесь не проверялись.

Самый изолированный путь: установить allin1 в отдельное окружение по [инструкции проекта](https://github.com/mir-aidj/all-in-one#installation), сохранить версии зависимостей и конфигурацию, выполнить его CLI там, затем импортировать JSON в основном окружении. Это позволяет оставить PyTorch, NATTEN, madmom и связанные зависимости вне Music Discovery. Базовый `pyproject.toml` не меняется. Совместимость Python/PyTorch/NATTEN нужно выбирать по актуальной документации; одной команды `pip install allin1` может быть недостаточно.

```bash
# В отдельно подготовленном окружении allin1:
allin1 /absolute/path/track.wav -o /absolute/path/structure -m harmonix-all -d cpu

# В основном окружении Music Discovery:
.venv/bin/python -m discovery.audio /absolute/path/track.wav \
  --track-id 'track-id' --release-id 'release-id' \
  --allin1-json /absolute/path/structure/track.json \
  --allin1-model harmonix-all --allin1-version 'recorded-model-or-checkpoint-revision' \
  --source-sha256 'sha256-of-the-original-WAV' \
  --external-config /absolute/path/allin1-config.json \
  --output artifacts/audio/track-with-structure.json
```

`allin1-config.json` — явно сохранённая конфигурация запуска, например `{"device":"cpu","package_version":"actual-installed-version","checkpoint_sha256":"actual-hash-if-recorded"}`. Значения в примере необходимо заменить фактическими; неизвестный хеш нельзя выдумывать. Импорт проверяет заявленный SHA исходного аудио, конечность чисел, порядок и диапазон временных меток, соответствие сильных долей битам, длину списка позиций и отсутствие пересечений сегментов. Допустимо отклонение до 50 ms за концом записи из-за дискретизации; метки сохраняются без скрытого обрезания. Неизвестные функциональные метки отклоняются.

Если allin1 уже установлен в текущем окружении, доступен явный запуск:

```bash
.venv/bin/python -m discovery.audio /absolute/path/track.wav \
  --track-id 'track-id' --release-id 'release-id' \
  --allin1 --allin1-model harmonix-fold0 --device cpu \
  --output artifacts/audio/track-with-structure.json
```

Только `--allin1` разрешает выполнение модели и возможную загрузку весов её библиотеками. Python-эквивалент: `analyze_allin1(path, record, allow_model_execution=True)`. Временные стемы и спектрограммы создаются в отдельной временной папке. Сообщения прогресса, включая дочерние процессы, направляются в stderr. В результате сохраняются модель, версия установленного пакета, параметры, хеш нормализованного ответа; недоступный хеш весов отмечается неизвестным. Версия пакета не выдаётся за известную ревизию весов.

Структура сохраняется отдельно в `structure`, с `evidence_kind=model_prediction_not_verified_annotation`. Предсказанная секция `verse` — не эталонная аннотация и не признак «есть рэп». В основной `features` названия секций и эталонные ответы не попадают.

## Необязательные стемы Demucs

Адаптер принимает два явно переданных WAV: предполагаемый вокальный стем и инструментальную часть. Сам Demucs не запускается и не импортируется. Внешнее разделение можно выполнить в отдельном окружении официальным режимом [`--two-stems=vocals`](https://github.com/facebookresearch/demucs#separating-tracks); исходный репозиторий архивирован, поэтому окружение и версии следует сохранять отдельно.

```bash
# Отдельное окружение Demucs, только если разделение действительно нужно:
python -m demucs --two-stems=vocals -n htdemucs -d cpu /absolute/path/track.wav

# Основное окружение: измерить уже существующие файлы:
.venv/bin/python -m discovery.audio /absolute/path/track.wav \
  --track-id 'track-id' --release-id 'release-id' \
  --vocals /absolute/path/separated/vocals.wav \
  --instrumental /absolute/path/separated/no_vocals.wav \
  --demucs-model htdemucs --demucs-version 'recorded-model-or-checkpoint-revision' \
  --source-sha256 'sha256-of-the-original-WAV' \
  --external-config /absolute/path/demucs-config.json \
  --output artifacts/audio/track-with-stems.json
```

В `stems.vocals` и `stems.instrumental` появляются независимые измерения с собственными SHA-256, частотой дискретизации и происхождением. Длительности должны совпадать с оригиналом с точностью 50 ms. Роли заданы оператором, а не установлены детектором голоса. Привязка результата разделения к оригиналу заявлена оператором и не доказывается одним хешем. Тихий стем допускается с `status=silent`; это не подтверждение отсутствия вокала. Утечки между стемами и их относительное усиление остаются неизвестными. Demucs может независимо изменять уровни стемов, поэтому отношение их RMS здесь не считается долей вокала.

## Проверки

```bash
.venv/bin/python -m pytest -q tests/audio
.venv/bin/ruff check src/discovery/audio tests/audio
```

Проверяются четыре PCM-разрядности, разные частоты синусоид, противофазное стерео, тишина/короткие/повреждённые записи, явные ID и SHA, отсутствие импорта ML-пакетов в обычном запуске, строгая проверка внешней структуры и происхождения, сохранение неизвестных значений, раздельные стемы и чистый JSON при выводе прогресса дочерним процессом. Это проверка корректности адаптера, а не оценка качества allin1/Demucs на музыке.
